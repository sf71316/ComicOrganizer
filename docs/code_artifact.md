# 專案需求規格書：輕量級單機漫畫截圖搜尋系統

## 1. 專案目標與範疇

### 核心目標
打造一套運行於單機環境的「漫畫截圖搜尋引擎（Image Copy Detection / Instance Retrieval）」。使用者輸入任意一張漫畫截圖（整頁、單格分鏡或局部裁切），系統能從本地龐大的漫畫圖庫中，精準回傳該截圖所屬的**作品名稱、卷數／話數、頁碼及分鏡位置**。

### 範疇界定
* **包含（In-Scope）**：
  * 從已建立索引的本地漫畫圖庫（壓縮檔或圖片資料夾）中精準比對原頁。
  * 支援圖庫的**增量更新**（新增、替換、刪除單本漫畫時無須重建整個資料庫）。
  * 抗干擾能力：需能應對解析度縮放、壓縮雜訊、黑／白留白邊框、單格裁切，以及不同語言版本的對話框嵌字差異（如日文生肉建庫、中文漢化截圖搜尋）。
* **不包含（Out-of-Scope）**：
  * 不需要具備「跨作品畫風辨識」能力（即不要求猜測未收錄於圖庫中的作品作者）。
  * 不需要雲端部署、分散式叢集或多人高併發支援。

## 2. 功能需求（Functional Requirements）

### 2.1 離線建庫與增量維護
1. **多元格式串流讀取**：支援直接掃描本機資料夾，並以記憶體串流方式讀取 `.cbz`、`.cbr`、`.zip`、`.7z` 壓縮檔及散裝圖片（`.jpg`、`.png`、`.webp`），建庫過程不應產生大量硬碟暫存檔。
2. **檔案指紋與增量掃描**：計算檔案雜湊值（如 `XxHash64` / `XxHash3`），定期或手動觸發掃描時，僅針對新增或異動的漫畫進行處理；當檔案被移除或替換版本時，能依 `manga_id` 精準刪除舊有向量與 Metadata。
3. **整頁與分鏡雙重索引**：
   * 建庫時除了索引「整頁原圖」，須先透過分鏡偵測模型切出每頁的獨立分鏡格子，過濾面積過小的雜訊框後一併建立索引。
   * 記錄每個分鏡在原頁中的正規化座標 `(x, y, w, h)`。

### 2.2 即時以圖搜圖
1. **查詢前處理**：自動偵測並裁切截圖周圍的純黑、純白播放器／手機狀態列留白邊框。
2. **向量相似度檢索**：將查詢截圖轉換為特徵向量，於向量索引中檢索 Top-K 最相似候選結果。
3. **極端裁切精排（選配／可開關）**：當 Top-1 餘弦相似度低於高信心門檻（例如僅截了角色的半張臉）時，可對 Top-10 至 20 候選圖進行輕量級局部特徵比對（如 OpenCV ORB）以提升命中率。
4. **結果輸出**：回傳 Top-N 命中清單，包含相似度分數、作品與檔案路徑、頁碼、縮圖預覽，以及原頁上的分鏡高亮框。

## 3. 非功能性需求與系統限制（Non-Functional Requirements）

| 項目 | 規格與限制 |
| :--- | :--- |
| **部署架構** | **零外部服務（Embedded / Zero-Server）**。不依賴 Docker、獨立資料庫主機或常駐 Python 後端，目標打包為單一 C# 執行檔與本地資料檔。 |
| **開發技術** | 以 **C#（.NET 8 / 9）** 為主體；AI 模型僅在開發準備階段透過 Python 匯出為 `.onnx` 格式，執行期由 .NET 原生載入推論。 |
| **目標規模** | 需能流暢擴展至 **10,000 本單行本以上**（約 200 萬頁、含分鏡約 **1,000 萬筆向量**）。 |
| **硬體與資源控制** | 1. **待機 0 VRAM**：僅在批次建庫時啟用 GPU 推論，完成即釋放顯卡記憶體；單張截圖查詢可改以 CPU 執行。<br>2. **低記憶體佔用**：百萬級以上向量須支援量化（如 Int8）與磁碟記憶體映射（MMap），閒置 RAM 佔用目標控制在數百 MB 以內。 |
| **效能目標** | 1. **增量建庫**：單本 200 頁漫畫（約 1,000 分鏡）於中階消費級 GPU 上處理時間小於 10 秒。<br>2. **查詢延遲**：純向量搜尋小於 100 毫秒；純 CPU 端到端（含前處理與推論）小於 500 毫秒。 |

## 4. 初步技術選型與架構參考

### 建議技術堆疊（C# 生態系）
* **AI 推論引擎**：`Microsoft.ML.OnnxRuntime.DirectML`（免裝 CUDA Toolkit）或 `Microsoft.ML.OnnxRuntime.Gpu`
* **預訓練模型（ONNX）**：
  * 分鏡偵測：`YOLO11n`（漫畫分鏡權重，約 6 MB）
  * 特徵提取：`DINOv2-Small`（384 維）或 `Meta SSCD`（512 維，專為拷貝偵測與抗疊字設計）
* **本地關聯資料庫**：`Microsoft.Data.Sqlite`（儲存作品路徑、頁碼、分鏡座標、檔案雜湊）
* **嵌入式向量引擎**（二選一或分階段採用）：
  * 中小規模（$< 50$ 萬分鏡）：`sqlite-vec`（與關聯資料整合於單一 `.db` 檔）
  * 百萬級規模：`Cloud.Unum.USearch`（原生 HNSW 引擎，支援 Int8 量化、MMap 與增量寫入）
* **影像與壓縮檔處理**：`SharpCompress` + `SkiaSharp`（或 `OpenCvSharp4`）
* **並行管線**：利用 `System.Threading.Channels` 拆分「I/O 解壓縮 → GPU 批次推論 → DB 批次寫入」三階段非同步管線。

### 預期本機檔案結構
```text
MangaSearch/
├── MangaSearch.exe          # C# 主程式（桌面 UI 或本機 Web API）
├── models/
│   ├── panel_detector.onnx  # 分鏡偵測模型
│   └── feature_embed.onnx   # 影像特徵提取模型
└── data/
    ├── manga.db             # SQLite Metadata
    └── panels.usearch       # 向量索引檔（若採 sqlite-vec 則合併於 manga.db）
```

## 5. 領域特定技術挑戰

1. **黑白線稿與網點（Screentone）特性**：漫畫缺乏色彩資訊，且掃描版與電子版之間常存在網點摩爾紋（Moiré）與底色泛黃差異，特徵提取模型必須對結構與線條高度敏感，而非依賴色彩分佈。
2. **跨語言嵌字干擾**：同一頁的日文原版與漢化版在對話框文字排版、字體粗細甚至手繪狀聲詞上均有差異，模型需具備對局部文字覆蓋的高容錯度。
3. **極端局部裁切**：使用者常僅截取單一分鏡中的局部區域（如角色表情包），需評估純全局向量（Global Embedding）在此情境下的召回率極限。

## 6. 待評估之可行性研究項目（供 AI 審查用）

請針對上述需求書，從實作角度評估以下關鍵風險並提供具體建議或替代方案：

1. **模型選擇與 ONNX 轉檔可行性**：
   * 在「黑白漫畫 + 跨語言嵌字 + 局部裁切」的場景下，`DINOv2-Small` 與 `Meta SSCD` 兩者的實際檢索精度比較？是否有更適合漫畫領域的輕量開源模型？
   * 現有開源的漫畫分鏡偵測模型（如 YOLO 社群權重或 Magi）在轉換為 ONNX 並於 C# `OnnxRuntime` 執行時，是否存在動態形狀（Dynamic Shapes）或特殊算子不相容問題？
2. **C# 嵌入式向量庫的穩定性與擴展性**：
   * `Cloud.Unum.USearch` 的 C# NuGet 套件在 Windows 環境下對 **Int8 量化、MMap 掛載、以及頻繁增量 `Upsert` / `Remove`** 的實際穩定性與記憶體回收表現如何？（例如刪除舊向量後是否會造成索引膨脹需要定期重整？）
   * 在 1,000 萬筆 384 維向量的規模下，單機 SSD 搭配 MMap 的實際查詢延遲與 Recall@10 預估表現為何？
3. **OnnxRuntime 顯卡記憶體釋放機制**：
   * 在 C# 中使用 `OnnxRuntime.DirectML` 或 `.Gpu` 時，動態建立並 `Dispose()` `InferenceSession` 是否真的能徹底釋放 VRAM（做到待機 0 VRAM）？還是需要透過獨立的子行程（Worker Process）來確保顯卡記憶體完全歸還作業系統？
4. **無深度學習精排（Reranker）的精度底線**：
   * 若為了輕量化放棄 LightGlue，改用純 CPU 的傳統演算法（如 OpenCV ORB / AKAZE）對 Top-20 候選圖做複檢，在黑白漫畫線稿與跨語言嵌字的條件下，關鍵點匹配是否容易失效？是否有更合適的輕量精排策略？
5. **最小可行原型（MVP）驗證路線**：
   * 請規劃一個 1 至 2 週內可驗證核心假設的 MVP 實作步驟與評測指標（例如如何建立包含原圖、裁切圖、異語言圖的測試集來量化 Top-1 / Top-5 準確率）。
